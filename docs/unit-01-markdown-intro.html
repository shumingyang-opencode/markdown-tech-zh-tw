1.1 定義：Markdown 是什麼

Markdown 是由 John Gruber 於 2004 年提出的輕量標記語言（lightweight markup language）：用接近純文字的標記符號（如 #、**、-），寫出可被轉成 HTML 的結構化文件。設計哲學是「易寫易讀，隨處可渲染」。

一句話：Markdown = 「用打字就寫得出結構化文件」的格式。輸入是純文字、輸出是 HTML。
對比Word純文字Markdown
所見即所得是否半（預覽）
原始檔可讀否（二進位）是是
版本控制友善差好極佳
轉 HTML需匯出需手寫一鍵
學習成本中—極低

1.2 Markdown 與 HTML 的關係

Markdown 的「底層」就是 HTML：每種 Markdown 語法都對應一段 HTML。理解「誰優先」是關鍵：

  • 行內 HTML 優先於 Markdown：<span>、<div> 等 HTML 標籤可以直接寫在 Markdown 裡。
  • 區塊層級：HTML 區塊前後要空一行；有些渲染器要求 HTML 區塊內不能用 Markdown（依實作而定）。
  • 空白與跳脫：<div> 前若緊貼文字，會被當成行內元素。

渲染結果 · RENDERED

重點：只要渲染器支援，Markdown 與 HTML 可以混用——用 Markdown 寫 95%，用 HTML 補那 5% 的特殊排版。

1.4 設計哲學：為什麼 Markdown 會贏

  1. 原始檔可讀：沒開渲染器也能讀懂文件結構。
  2. 純文字：任何編輯器、任何系統都能開；不會壞檔。
  3. 版本控制友善：git diff 看得到「改了哪一行」——Word 辦不到。
  4. 隨處渲染：同一個 .md 可變 GitHub 頁、網站、PDF、筆記。
  5. 永不過時：語法少而穩定，20 年後仍可用。
常被忽略的點：Markdown 沒有「標準」單一規格——各渲染器對細微語法（如巢狀清單、表格）略有差異。寫重要文件前先確認目標渲染器（尤其 GFM）。

進階真實情境 Worked Example

情境：用 Markdown 自動產生 Changelog 並同步到 GitHub Release

假設你有一個專案，每次發版都要從 git log 產生 Changelog。以下是一條完整的命令序列：

終端 · TERMINAL
# 1. 取得上一個 tag 以來的所有 commit
git log $(git describe --tags --abbrev=0)..HEAD \
  --pretty=format:"- %s (%h)" > changes.md

# 2. 在開頭插入標題與分類
sed -i '1i\## [v1.3.0] - 2026-08-17\n\n### Changed\n' changes.md

# 3. 把帶有 #bug 的 commit 歸入 Fixed 分類
git log $(git describe --tags --abbrev=0)..HEAD \
  --grep="#bug" --pretty=format:"- %s (%h)" | \
  sed 's/^/- /' > bugs.md
echo -e "\n### Fixed\n$(cat bugs.md)" >> changes.md

# 4. 用 pandoc 轉成 HTML（可嵌入 GitHub Release body）
pandoc changes.md -o changes.html

cat changes.md
模擬輸出 · OUTPUT
## [v1.3.0] - 2026-08-17

### Changed
- 新增 dark mode 支援 (a1b2c3d)
- 升級 dependencies (e4f5g6h)

### Fixed
- 修正登入逾時問題 (i7j8k9l)
- 修正匯出 CSV 編碼 (m0n1o2p)

為什麼選這條路徑：手動從 git log 複製貼上容易漏 commit 且格式不一致。用 git log --pretty=format 統一輸出格式，再用 sed 插入 Markdown 標題結構，最後用 pandoc 轉 HTML——三步全自動、可寫進 CI script，每次發版跑一次就不會漏。

替代方案比較：也可用 conventional-changelog 或 release-please，但它們要求 commit 遵循 Conventional Commits 規範。如果你的團隊沒在管 commit 格式，上面的手動方法更彈性。

深入原理擴充

Markdown 渲染引擎的內部運作

當你按下「預覽」，渲染引擎（如 marked、markdown-it、CommonMark）內部其實在跑一套多階段管線（pipeline）：

  1. 區塊解析（Block Parsing）：用正則逐行掃描，判斷每一行是標題、段落、清單項、代碼圍欄、還是 HTML 區塊。遇到 # 開頭就標記為 ATX Heading；遇到 - 或 * 開頭且在清單上下文中就延續清單。
  2. 行內解析（Inline Parsing）：在段落文字內掃描 **、*、`、[、! 等行內標記，用正則拆成 token 串。
  3. AST 構建：把 token 串組成抽象語法樹（Abstract Syntax Tree），每個節點是標題、段落、強調等。
  4. HTML 生成：遍歷 AST，每個節點轉成對應的 HTML 標籤。
容易忽略的邊界案例：行內解析是貪婪匹配的——**a** b **c** 會正確渲染為「a b c」，但 **a *b** c* 在部分渲染器會產生不預期的結果，因為巢狀強調的開合順序不符合「先開後關」規則。建議：巢狀強調時，內層標記要完全包在外層標記內部，不要交叉。

診斷式疑難排解表

症狀可能原因解決方案
標題沒顯示，直接出現在正文# 後面沒有空格改為 # 標題（# 後加一個空格）

進階挑戰題

挑戰 1：寫一份「Markdown vs HTML vs reStructuredText」的三方比較表格（至少 6 個比較維度），包含對齊方式不同的欄位。然後用參照式連結把每個工具連結到官網。
挑戰 2：用 Markdown 寫一份「公司內部 Markdown 風格指南」，內容包含：標題層級規範、強調符號選擇、清單縮排標準、程式碼區塊命名約定。至少使用 3 種不同的 Markdown 區塊語法（表格、引用、代碼區塊）。
挑戰 3：從一個真實的 git repo（你自己的專案也行）執行 git log --oneline -20，然後用純 Markdown 把這 20 個 commit 整理成分類的 Changelog（Changed / Fixed / Added），練習「原始資料 → 結構化文件」的轉換。

① 專案級端到端 Worked Example

專案：my-docs 文件站 — 從零建立 → 自動化檢查 → 部署

這個專案整合本單元「原始檔可讀、版本控制友善、隨處渲染」三大核心概念：一份 Markdown 文件同時服務「人讀」（README）、「機器檢查」（markdownlint）與「網站」（GitHub Pages）三種用途。

$ git log --oneline -3

為什麼這是「專案級」：它不是單一語法示範，而是把「格式選型、目錄結構、品質門檻、CI 部署」串成一套可交付的系統——Markdown 的角色從「寫文件的格式」升級為「整個文件系統的原始碼」。讓專案「活」起來的三個時刻：他人 clone 後不開任何工具就能讀懂 README；make check 在 CI 擋住所有語法錯誤；git push 後幾秒內 GitHub Pages 出現更新後的文件站。

與第 1 輪範例的層級差異：第 1 輪是在「檔案內」完成一件事（產生 Changelog）；這裡是在「整個 repo」層面完成一套系統——原始檔、檢查、部署三位一體，是量級上的跳躍。

② 效能/品質/安全深度

本單元主題：品質 — 渲染一致性的治理

Markdown 沒有單一規格，同一份文件在不同渲染器可能長得不同。品質治理的核心不是追求「唯一真理」，而是「鎖定目標渲染器」：

  • 宣告規格：在 CONTRIBUTING 明寫「本 repo 遵循 CommonMark + GFM」，新成員照著寫。
  • 自動化檢查：markdownlint 的 MD024（重複標題）、MD013（行長）在 CI 統一把關。
  • 渲染快照測試：把「已渲染 HTML」存成 snapshot，升級渲染引擎後用 git diff 看出行為變化。
  • 人審節點：重要文件（README、SLA）仍需 PR 審查——人是最後一道防線。
常見誤區：「多用 HTML」不等於「品質好」——混入大量 <div>/<style> 會讓原始檔失去可讀性，且換渲染器時最容易壞。能用 Markdown 表達的 95% 用 Markdown，HTML 只留給無可取代的 5%。
