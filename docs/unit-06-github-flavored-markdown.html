6.1 什麼是 GFM

GitHub Flavored Markdown（GFM） 是 GitHub 在標準 Markdown 上擴充的方言，也是「在 GitHub 協作」的實際標準。它涵蓋：任務清單、刪除線、自動連結、表格（規範化）、註腳、emoji、內嵌 HTML、忽略 Markdown。

為什麼重要：你在 GitHub 寫的 README、Issue、PR、Wiki 全部用 GFM。學會它等於學會「在 GitHub 溝通」。

6.2 任務清單 · Task List

原始碼 · SOURCE
- [x] 完成安裝
- [ ] 撰寫 README
- [ ] 發佈 v1.0
渲染結果 · RENDERED
完成安裝
撰寫 README
發佈 v1.0
注意：任務清單必須是清單的子項，[ ]（未勾）與 [x]（已勾）中間要空格。可巢狀（子任務）且可在 Issue/PR 中被 GitHub 自動統計。

6.3 刪除線 · Strikethrough

原始碼 · SOURCE
~~舊方案~~ 已改為新方案
渲染結果 · RENDERED
舊方案 已改為新方案

6.4 自動連結 · Autolink

GFM 自動把 URL、#issue、@mention、commit SHA 轉成可點連結：

原始碼 · SOURCE
網址 https://github.com 自動變連結。
修復了 #123 的問題。
感謝 @team 的協助。
渲染結果 · RENDERED

網址 https://github.com 自動變連結。
修復了 #123 的問題。
感謝 @team 的協助。

6.5 註腳與 emoji

原始碼 · SOURCE
這是有註腳[^1]的句子。

[^1]: 註腳內容說明。

發佈成功 :tada: :rocket:
渲染結果 · RENDERED

這是有註腳1的句子。
發佈成功 🎉 🚀

Emoji 短碼：:tada: :rocket: :bug: :warning: 等。支援不全的渲染器會原樣顯示短碼。

6.6 忽略 Markdown 語法（跳脫）

想在文件裡「顯示」Markdown 符號而非「觸發」它，用反斜線 \ 跳脫：

原始碼 · SOURCE
\*這不是斜體\*
\# 這不是標題
用 \` 顯示反引號
渲染結果 · RENDERED

*這不是斜體*
# 這不是標題
用 ` 顯示反引號

進階真實情境 Worked Example

情境：撰寫一份完整的 Release Notes（含任務清單追蹤進度）

假設 v2.0.0 發佈，你要把 CHANGELOG 整理成 GitHub Release Notes，包含：已完成/未完成項目、關聯 Issue、貢獻者感謝：

原始碼 · SOURCE
## v2.0.0 Release Notes (2026-08-17)

### 🎉 新功能
- [x] 支援 dark mode :crescent_moon:
- [x] 新增匯出 PDF 功能 #102
- [ ] 多語言 i18n 支援 #115 *(延後至 v2.1)*

### 🐛 修正
- ~~修正登入逾時（舊方案：固定 30s）~~ → 改用動態 token 刷新 #98
- 修正 CSV 匯出編碼問題 #101

### 📦 依賴升級
- `react` 18.2 → 18.3
- `typescript` 5.4 → 5.5

### 👏 感謝
@alice 貢獻了 dark mode 的設計稿，
@bob 修正了三個 critical bug。
完整變更見 [CHANGELOG](../CHANGELOG.md)。
渲染結果 · RENDERED

v2.0.0 Release Notes (2026-08-17)

🎉 新功能

  • 支援 dark mode 🌙
  • 新增匯出 PDF 功能 #102
  • 多語言 i18n 支援 #115 (延後至 v2.1)

🐛 修正

  • 修正登入逾時（舊方案：固定 30s） → 改用動態 token 刷新 #98
  • 修正 CSV 匯出編碼問題 #101

📦 依賴升級

  • react 18.2 → 18.3
  • typescript 5.4 → 5.5

👏 感謝

@alice 貢獻了 dark mode 的設計稿，@bob 修正了三個 critical bug。完整變更見 CHANGELOG。

為什麼選這條路徑：任務清單讓讀者（與團隊）一眼看出哪些已完成、哪些延後；刪除線 + 文字說明展示「從舊方案到新方案」的演進；#102 自動連結到對應 Issue；@mention 自動通知貢獻者。一個 Release Notes 同時用了 GFM 的四大特色。

深入原理擴充

GFM 解析器的內部處理順序

GFM 在標準 Markdown 基礎上增加了多個擴充，解析順序如下：

  1. 表格解析：先於行內處理——遇到 | 分隔的行且第二行是 --- 模式時，整段被標記為表格節點。
  2. 任務清單：在清單解析階段，檢查每個 - 或 * 項目後面是否跟著 [ ] 或 [x]，是則生成 checkbox。
  3. 自動連結：在行內解析後期，掃描文字中的 URL 模式，轉成 <a href>。
  4. Emoji 短碼：最後一步，把 :shortcode: 替換為 Unicode emoji 字元。
容易忽略的邊界案例：自動連結的 URL 匹配是貪婪的——如果 URL 後面緊跟著標點（如句號或逗號），有些渲染器會把標點也抓進 URL，導致連結失效。例如 Visit https://example.com. 可能變成連結包含結尾句號。解法：在 URL 後加一個空格，或用行內 code 包住 URL。

診斷式疑難排解表

症狀可能原因解決方案
任務清單沒顯示 checkbox[ ] 不在清單項目開頭確保 - [ ] 是行首（- 後空格再 [）
#123 沒變成連結不在 GitHub 環境中GFM 自動連結僅在 GitHub 渲染器生效；其他環境用 #123 無法自動連結
腳註顯示 [^1] 原文渲染器不支援 GFM 註腳改用 HTML <sup> 或手動在文末放說明
Emoji 短碼原樣顯示渲染器不支援 emoji 短碼替換直接使用 Unicode emoji 字元（🎉）替代短碼
刪除線和任務清單衝突~~[x] task~~ 先解析刪除線再解析 checkbox不要在任務清單項目上套用刪除線

進階挑戰題

挑戰 1：建立一個「Sprint 回顧」文件，包含：已完成的任務清單（至少 5 項，含 1 項巢狀子任務）、未完成的任務（未勾選）、被放棄的需求（用刪除線標記）、3 個關聯 Issue 的自動連結、1 位被 @mention 的貢獻者。
挑戰 2：在同一份文件中混合使用 GFM 的所有擴充語法：任務清單、刪除線、自動連結、emoji 短碼、表格、腳註。然後把這份文件分別在 GitHub 和一個不支援 GFM 的 Markdown 編輯器中預覽，記錄渲染差異。
挑戰 3：寫一份「GFM vs Standard Markdown vs CommonMark」的三方比較表格（至少 7 個比較維度），用參照式連結分別連結到三份規範文件。然後在文末加一個腳註說明你的偏好。

① 專案級端到端 Worked Example

專案：開源專案協作範本 — 一份 repo 從 README 到 Issue/PR 模板的完整 GFM 套件

開源專案的每一面（README、Issue、PR、CHANGELOG）都是用 GFM 溝通的介面。這個專案把 GFM 的任務清單、自動連結、@mention、表格全部整合成一套「協作入門包」。

產出檔案樹 · FILE TREE
awesome-tool/
├── README.md
├── CONTRIBUTING.md     ← 本篇重點（任務清單）
├── ISSUE_TEMPLATE/
│   ├── bug_report.md
│   └── feature_request.md
├── PULL_REQUEST_TEMPLATE.md
├── CHANGELOG.md
└── .github/
    └── dependabot.yml
bug_report.md · KEY FILE
## 問題描述
- [ ] 已搜尋現有 issue（#102 相關）

**重現步驟**
1. 執行 `awesome-tool run`
2. 觀察 `Error 500`

**環境**：macOS 14 · v1.2.0 :bug:

**預期**：正常輸出
**實際**：拋出例外

相關：@maintainer 請協助分類。
CONTRIBUTING.md · KEY FILE
# 貢獻指南

## 第一次貢獻
- [ ] Fork 並 clone
- [ ] 建立分支
- [ ] 撰寫測試
- [ ] 發 PR（closes #N）

## 程式碼風格
| 項目 | 規範 |
|:-----|:-----|
| 縮排 | 2 空格 |
| 命名 | camelCase |

> ⚠️ PR 未通過 CI 不會被合併。
驗證 · VERIFY (GitHub)

✅ 任務清單在 Issue 顯示進度條
✅ #102、@maintainer 自動變連結
✅ PR body 的 closes #N 合併時自動關閉 issue
✅ 表格在 README 中正確對齊渲染

為什麼這是「專案級」：單一文件的 GFM 語法很容易，難的是「整 repo 的溝通用語一致」——Issue 模板確保每份 bug report 結構相同、CHANGELOG 讓每個版本都有可比性。這是一套「用 GFM 規範協作文化」的系統。

與第 1 輪範例的層級差異：第 1 輪是「一份 Release Notes」；這裡是「整個 repo 從第一天就用 GFM 定義好協作介面」——模板即文件、文件即規範。

② 效能/品質/安全深度

本單元主題：品質 — GFM 跨平台渲染一致性

GFM 是 GitHub 的方言——同一份文件在 GitLab、VS Code 預覽、GitBook 上渲染結果可能不同：

  • 表格：GFM 表格被 GitLab、VS Code 支援，但傳統 Markdown 與部分編輯器不支援。
  • 註腳：[^1] 在 GitHub 支援，但 VS Code 預覽與多數編輯器不支援——會顯示原文。
  • 任務清單：- [x] 在 GitHub 渲染為可點擊 checkbox，其他平台多為純文字。
  • 策略：需要跨平台的文件，用「CommonMark + GFM 交集」寫法（Core Syntax + 表格），並在 README 標明目標平台。
一致性檢查：同一份文件至少在「GitHub + 你常用的本地預覽器」各渲染一次並對照。把「哪裡支援、哪裡不支援」寫進團隊的風格指南，比事後逐篇修還有效率。
