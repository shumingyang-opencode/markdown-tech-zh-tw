8.1 完整 README 實作

一份好的 README 有固定骨架。以下是一次完整的實作，逐段拆解：

README.md · SOURCE
# my-tool

[![build](https://img.shields.io/badge/build-passing-brightgreen)](https://ci.example.com)

用一句話說明這個工具**做什麼、解決什麼問題**。

## 功能
- 快速、輕量
- 支援 CLI 與 API

## 安裝
```bash
npm install -g my-tool
```

## 使用
```bash
my-tool run --config config.yaml
```

- [API 參考](docs/api.md)

8.2 常見錯誤清單

錯誤原因修正
按 Enter 沒換行段落需空行加空行，或行尾兩空格
巢狀清單跑掉縮排不足/不統一統一用 2 或 4 空格

8.4 風格指南建議

  • 一個 H1：文件只有一個主標題，其餘用 H2+。
  • 星號強調：**/*，不用底線。
  • 圍欄式程式碼：一律指定語言。
  • 清單符號一致：全站統一 -。
  • 表格欄數一致：可讀性優先。
  • 換行用空行：少用行尾雙空格。

看完這單元你應該能說出：
  • 從零寫出一份結構完整的 README（含徽章/安裝/使用/授權）。
  • 避開常見錯誤（換行、縮排、反引號數目、表格欄數）。
  • 用 markdownlint 與工具鏈檢查文件品質。
  • 建立個人化的「交付前檢查清單」。

進階真實情境 Worked Example

情境：建立一個跨平台的完整 README 檢查腳本

在 CI/CD 中自動化 Markdown 品質檢查——整合 markdownlint + 圖片路徑驗證 + 連結檢查：

check-markdown.sh
#!/bin/bash
set -e

echo "=== Markdown 品質檢查 ==="

# 1. markdownlint 語法檢查（忽略 MD013 段落長度、MD033 HTML）
echo "[1/3] markdownlint 檢查..."
npx markdownlint-cli "docs/**/*.md" \
  --config .markdownlint.json || {
    echo "❌ markdownlint 失敗"
    exit 1
  }
echo "✅ markdownlint 通過"

# 2. 驗證所有本地圖片路徑存在
echo "[2/3] 圖片路徑驗證..."
MISSING=0
grep -rhoP '(?<=\()((?!\.\.?\./)(?!https?://)[^)]+\.(png|jpg|svg|gif))' \
  docs/*.md docs/**/*.md 2>/dev/null | sort -u | while read -r img; do
  if [ ! -f "docs/$img" ] && [ ! -f "$img" ]; then
    echo "  ❌ 缺少：$img"
    MISSING=$((MISSING + 1))
  fi
done
echo "✅ 圖片路徑檢查完成"

# 3. 檢查是否有未關閉的程式碼區塊
echo "[3/3] 程式碼區塊完整性..."
BAD=$(grep -rn '```' docs/*.md | awk -F: '{print NR}' | wc -l)
if [ $((BAD % 2)) -ne 0 ]; then
  echo "❌ 偵測到未關閉的程式碼圍欄"
  exit 1
fi
echo "✅ 程式碼區塊完整"

echo ""
echo "🎉 所有檢查通過！"
模擬輸出 · OUTPUT
=== Markdown 品質檢查 ===
[1/3] markdownlint 檢查...
✅ markdownlint 通過
[2/3] 圖片路徑驗證...
✅ 圖片路徑檢查完成
[3/3] 程式碼區塊完整性...
✅ 程式碼區塊完整

🎉 所有檢查通過！

為什麼選這條路徑：光靠 markdownlint 不夠——它不檢查圖片路徑是否存在，也不檢查未關閉的程式碼圍欄。把三個檢查串成一個 script，一次跑完涵蓋語法、路徑、結構三個面向。整合進 CI 後，每次 PR 都會自動驗證。

為什麼不用現成工具：也可以用 lychee（跨平台連結檢查器）或 markdown-link-check，但它們主要是檢查外部 URL 是否存活。上面的腳本更專注於「本地 Markdown 結構正確性」——這正是多數工具忽略的面向。

深入原理擴充

Markdown 轉換工具（pandoc / markitdown）的內部處理

當你用 pandoc input.md -o output.html 時，內部發生的事：

  1. 詞法分析（Lexing）：把 Markdown 文字拆成 token 串——標題 token、段落 token、強調 token、代碼圍欄 token 等。
  2. 語法分析（Parsing）：把 token 串組成 AST（抽象語法樹）。例如 # Title 變成 Header(1, [], [Str "Title"])。
  3. 轉換（Transform）：可選的 AST 轉換步驟——pandoc 的過濾器（filters）在這裡介入，可以新增/修改/刪除節點。
  4. 輸出生成（Writing）：遍歷 AST，根據目標格式（HTML/LaTeX/DOCX）生成對應輸出。
容易忽略的邊界案例：pandoc 預設不會把 Markdown 中的 < 當成 HTML——它會先嘗試當成 Markdown 行內元素。要讓 pandoc 正確處理 HTML，需要加 --from markdown+raw_html。而 markitdown 的方向相反：它把 HTML/PDF/DOCX 轉回 Markdown，內部用的是相反的管線（HTML 解析 → Markdown 生成）。

診斷式疑難排解表

症狀可能原因解決方案
markdownlint 報告 MD033（不允許內嵌 HTML）預設規則禁止 HTML，但你的文件確實需要在 .markdownlint.json 設定 "MD033": false 關閉此規則
pandoc 轉 HTML 後圖片路徑全壞用相對路徑，但輸出的 HTML 在不同目錄加 --resource-path=. 或改用絕對 URL
markitdown 轉出的 Markdown 表格欄寬全亂原文件的表格是用 HTML <table> 寫的markitdown 會盡力轉換，但複雜 HTML 表格建議手動調整
CI 中 npx markdownlint-cli 找不到沒安裝或沒加到 package.json執行 npm install -D markdownlint-cli 或用 npx --yes
GitBook / Notion 轉 Markdown 後格式崩壞這些平台的 Markdown 是私有擴充，不是標準 GFM用 markitdown 轉出後手動修正，或用 pandoc 做中繼轉換

進階挑戰題

挑戰 1：建立一個完整的「交付前 Markdown 檢查清單」腳本，涵蓋：markdownlint 語法、所有相對路徑連結可點、所有圖片存在、程式碼圍欄已關閉、表格欄數一致、H1 只有一個。腳本跑完後輸出一份 JSON 格式的檢查報告。
挑戰 2：寫一份「從 Notion 遷移到 Markdown」的完整指南：先用 markitdown 把 Notion 匯出的 HTML 轉成 Markdown，然後列出 10 個常見的格式問題（如 Notion 的 toggle block 轉成 <details> 的差異），每個問題附上修正前後的對比。
挑戰 3：建立一個 GitHub Actions workflow，在每次 PR 修改 .md 檔時自動執行：(1) markdownlint 檢查、(2) 連結存活檢查、(3) 圖片大小檢查（超過 500KB 警告）。把 workflow 設定檔和一份範例 README 一起放在 repo 中。

① 專案級端到端 Worked Example

專案：全站文件品質自動化系統 — 從檢查到報告，讓品質可度量

單元 8 是終點站——把前面所有單元學到的「正確用法」轉成一套可重複執行的品質系統：lint、路徑檢查、結構校驗、品質報告，全部自動化。

產出檔案樹 · FILE TREE
docs-quality/
├── .markdownlint.json     ← 規則設定
├── scripts/
│   ├── check-all.sh       ← 整合所有檢查
│   ├── check-links.sh
│   └── report.py          ← 產出 JSON 品質報告

quality.yml · KEY FILE
name: quality
on: pull_request

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npx markdownlint-cli "docs/**/*.md"
      - run: ./scripts/check-links.sh
      - run: python3 scripts/report.py
      - run: |
          if [ -s quality-issues.txt ]; then
            cat quality-issues.txt && exit 1
          fi

① 規則集中於 .markdownlint.json
② 多項檢查整合進一個 script
③ 產出可機器讀的 JSON 報告
④ CI 在 PR 合併前強制品質門檻

為什麼這是「專案級」：品質治理如果只靠「每個人自律」就會逐篇退化。這套系統把「檢查 → 度量 → 擋在合併前」變成工程常態——品質從「態度」變成「系統」，正是單元 8 全部工具鏈的總集成。

與第 1 輪範例的層級差異：第 1 輪是「一支檢查腳本」；這裡是「附 CI 閘門 + 品質報告的完整治理系統」——加了度量與阻擋機制，才算真正落地。

② 效能/品質/安全深度

本單元主題：品質 — 全站品質治理的機制設計

品質治理的關鍵不是「用哪個工具」，而是「機制是否閉環」：

  • 單一來源：一份風格指南（或 .markdownlint.json）是全站唯一規則來源，新成員照著跑。
  • 可度量的門檻：品質不能只靠感覺——「0 error gate」是明確門檻；警告（warnings）列入報告供審查。
  • 自動化優先：機器能檢查的（語法、路徑、結構）全部自動化，把人的精力留給「語意正確性」。
  • 例外處理：某些檔案需要關閉特定規則時，用行內 <!-- markdownlint-disable --> 並附原因，而非全站放寬。
  • 回饋閉環：檢查結果回報到 PR 評論，作者當場修正——而不是月底一次大掃除。
常見誤區：規則開越多越好？不是。過嚴的規則會讓大家養成「關規則」的習慣，反而失去意義。只開「真正會害文件壞掉」的規則，其餘用警告等級。
