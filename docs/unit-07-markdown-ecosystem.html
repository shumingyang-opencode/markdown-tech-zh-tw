7.1 GitHub：README / Issue / PR

GitHub 是 Markdown 使用率最高的場合：README 是 repo 的首頁文件、Issue 是問題追蹤、PR 是變更討論。三者都用 GFM。

  • README：首頁名片——專案做什麼、怎麼裝、怎麼用。
  • Issue：問題回報與功能請求（搭配 template 自動化結構）。
  • PR：變更說明、測試結果、關聯 issue（closes #12 自動關閉）。

7.2 靜態網站 · Static Sites

靜態網站生成器（SSG）以 Markdown 為文章來源，配合 frontmatter（YAML 標頭）產出整站：

frontmatter · HUGO
---
title: "我的文章"
date: 2026-08-16
tags: ["markdown"]
---

這是**正文**。

7.3 筆記軟體 · Obsidian / Notion

Obsidian 以 Markdown 為儲存格式，支援雙向連結 [[筆記名]] 與 Graph View——你的筆記就是一堆可版本控制的 .md 檔；Notion 底層也是區塊式 Markdown。

7.4 Mermaid：在 Markdown 內畫圖

Mermaid 讓你在程式碼區塊（```mermaid）內用文字畫流程圖/序列圖/甘特圖，GitHub、GitLab、Obsidian 都支援：

原始碼 · SOURCE
```mermaid
flowchart LR
  A[開始] --> B{成功?}
  B -- 是 --> C[部署]
  B -- 否 --> D[回滾]
```
渲染結果 · RENDERED

A[開始] → B{成功?}
B --是--> C[部署]
B --否--> D[回滾]

（支援 Mermaid 的環境會渲染成圖形）

序列圖 · SEQUENCE
```mermaid
sequenceDiagram
  使用者->>伺服器: 登入
  伺服器-->>使用者: token
```
渲染結果 · RENDERED

使用者 → 伺服器: 登入
伺服器 → 使用者: token

7.5 Docs-as-Code 工作流

工作流 · WORKFLOW
1. Markdown 原始檔進 repo（docs/）
2. CI 執行 markdownlint + 建置
3. 發佈到靜態網站（GitHub Pages）
4. 文件與程式碼同 PR 審查

成果：文件可追溯、可自動化、永不過時。

7.6 AI 工具與 Markdown

現代 AI 工具（ChatGPT、Copilot、OpenCode）大量以 Markdown 作為輸入/輸出格式：

  • 輸入：把 repo 的 README/文件餵給 LLM 建立上下文。
  • 輸出：LLM 回傳結構化回答（標題、清單、程式碼區塊）。
  • AGENTS.md / CLAUDE.md：以 Markdown 寫的代理指令檔，已是工程主流。
意義：會寫 Markdown = 會跟 AI 工具「精準溝通」。這是新一代軟體工程師的基本功。

深入原理擴充

Markdown 渲染管線在靜態網站生成器中的位置

以 Hugo / VitePress / Astro 為例，完整的建置流程是：

  1. Frontmatter 解析：YAML/TOML 標頭被解析為頁面的元資料（title、date、tags），用於產生 <head> 標籤與導覽。
  2. Markdown → HTML：正文經渲染引擎（marked / markdown-it / unified）轉成 HTML 片段。
  3. 模板套用：HTML 片段被插入佈局模板（layout）的 {{ content }} 位置。
  4. 靜態資源處理：圖片、CSS、JS 被複製或打包。
  5. 輸出：每個 .md 生成對應的 .html，目錄結構反映 URL 路由。
容易忽略的邊界案例：frontmatter 的 date 欄位在 Hugo 中若寫成 date: 2026-8-17（月份沒補零），會解析失敗或被當成字串。正確寫法是 date: 2026-08-17。另外，某些 SSG 的 frontmatter 不支援巢狀物件（如 VitePress 的 hero.actions 需要用 YAML 的縮排格式，不是 JSON）。

診斷式疑難排解表

症狀可能原因解決方案
Mermaid 圖表顯示原始碼文字環境不支援 Mermaid（例如用 markdown-it 預設沒裝插件）確認 SSG 有安裝 mermaid 並啟用（VitePress 預設支援）
frontmatter 的中文標題變成亂碼檔案編碼不是 UTF-8用編輯器確保檔案以 UTF-8 編碼儲存
Docs-as-Code CI 失敗：markdownlint error規則過嚴（如 MD013 段落過長、MD033 內嵌 HTML）建立 .markdownlint.json 自訂規則，關閉不適用的檢查
頁面間連結 404用了相對路徑但 SSG 的 URL 結構不同改用 SSG 提供的絕對路徑或 /guide/quickstart 格式
GitHub Pages 部署後圖片壞掉repo 有子路徑（username.github.io/repo/），但資源路徑沒帶子路徑在 SSG config 設定 base: '/repo/'

進階挑戰題

挑戰 1：用 Markdown + frontmatter 建立一個 3 頁的迷你文件站結構：首頁（hero layout）、安裝指南、API 參考。每頁都有 YAML frontmatter（title、description、tags），頁面之間用相對連結互連。然後畫出 Mermaid 架構圖顯示頁面結構。
挑戰 2：設計一個完整的 Docs-as-Code 工作流：.md 文件 → markdownlint 檢查 → Hugo 建置 → GitHub Pages 發佈。寫出完整的 CI 設定（GitHub Actions YAML），包含：觸發條件、安裝步驟、lint、build、deploy。每一步都附註解說明。
挑戰 3：比較三種 SSG（Hugo / VitePress / mkdocs）對 Markdown 的支援差異：frontmatter 格式、表格語法、Mermaid 支援、程式碼高亮主題。用表格整理，並在最後用引用區塊寫出你的選擇建議與理由。
