2.1 標題 · Headings

用 # 到 ###### 表示六級標題。# 越多層級越低，建議 # 後加一個空格（GFM 強制）。

原始碼 · SOURCE
# 標題一
## 標題二
### 標題三
#### 標題四
##### 標題五
###### 標題六
渲染結果 · RENDERED

標題一

標題二

標題三

標題四

標題五

標題六

為什麼標題重要：標題是文件結構的骨架——多數渲染器自動產生目錄（TOC），且標題可被錨點連結（#標題）。一份文件應只有一個 H1。

2.2 強調 · Bold & Italic

原始碼 · SOURCE
**粗體**（雙星號）
*斜體*（單星號）
***粗斜體***（三星號）
~~刪除線~~（GFM）
__底線粗體__（可選）
渲染結果 · RENDERED

粗體（雙星號）
斜體（單星號）
粗斜體（三星號）
刪除線（GFM）
底線粗體（可選）

建議：粗體用 **、斜體用 *。底線 _ 在中文容易黏字、且與連結底線混淆，星號最直覺。巢狀強調如 **粗體內 *斜體*** 也合法。

2.3 段落與換行

段落之間用一個空行分隔；要在段落內強制換行，在行尾加兩個空格再 Enter。

原始碼 · SOURCE
第一段。

第二段（前面有空行）。

同一段內換行（行尾兩個空格）  
下一行還是同一段。
渲染結果 · RENDERED

第一段。

第二段（前面有空行）。

同一段內換行（行尾兩個空格）
下一行還是同一段。

最常見錯誤：只按一次 Enter 在 Markdown 不會換行（會被合併成同一段）。要開始新段落請留空行；行尾兩個空格對初學者易漏，建議多用空行。

2.4 無序清單 · Unordered Lists

用 -、*、+ 開頭。縮排四格（或兩格，但全站要一致）可做巢狀清單。

原始碼 · SOURCE
- 蘋果
- 香蕉
  - 芭蕉（縮排巢狀）
    - 再下一層
- 奇異果

* 用星號也可以
+ 用加號也可以
渲染結果 · RENDERED
  • 蘋果
  • 香蕉
    • 芭蕉（縮排巢狀）
      • 再下一層
  • 奇異果

（星號/加號渲染結果相同）

2.5 有序清單 · Ordered Lists

原始碼 · SOURCE
1. 先安裝
2. 再設定
   1. 子步驟 A（縮排）
   2. 子步驟 B
3. 最後執行
渲染結果 · RENDERED
  1. 先安裝
  2. 再設定
    1. 子步驟 A（縮排）
    2. 子步驟 B
  3. 最後執行
貼心設計：有序清單數字寫什麼都行，渲染時自動重新編號——全寫 1. 也能得到 1,2,3。但強烈建議寫正確數字：方便你「在原始檔直接看出順序」。
混用陷阱：在無序清單內夾有序清單、或反之，縮排要對齊到項目文字而不是標記符號，否則會跑版。

2.7 Worked Example：今日待辦

原始碼 · SOURCE
# 今日待辦

**優先事項：**
1. 完成單元 2
2. 練習清單

**其他：**
- 買菜
  - 青菜
  - 雞蛋

---

明天再想。**重點是** 先動手寫。
渲染結果 · RENDERED

優先事項：

  1. 完成單元 2
  2. 練習清單

其他：

  • 買菜
    • 青菜
    • 雞蛋

明天再想。重點是 先動手寫。

練習：把「今日待辦」改用 * 無序清單 + 巢狀 + 一段引用，觀察渲染差異。

看完這單元你應該能說出：
  • 寫出六級標題並說出 # 後要加空格。
  • 區分粗體 **、斜體 *、刪除線 ~~，並寫出巢狀強調。
  • 說明段落與段內換行的規則（空行 vs 行尾兩空格）。
  • 寫出有序/無序/巢狀清單，並說明有序清單自動編號的特性。

進階真實情境 Worked Example

情境：從 CSV 報表中提取異常行並產生結構化 Markdown 報告

假設有一份 sales.csv（欄位：日期、產品、數量、金額），你要找出「單筆金額超過 10000」的異常交易，並直接產出 Markdown 表格報告：

終端 · TERMINAL
# 1. 先看 CSV 結構
head -5 sales.csv

# 2. 用 awk 提取金額 > 10000 的行（假設第4欄是金額）
awk -F',' '$4 > 10000 {print}' sales.csv > anomalies.csv

# 3. 用 awk 把 CSV 轉成 Markdown 表格
echo "| 日期 | 產品 | 數量 | 金額 |"
echo "|------|------|------|-----:|"
awk -F',' '{printf "| %s | %s | %s | $%,d |\n", $1, $2, $3, $4}' \
  anomalies.csv

# 4. 統計總筆數與總金額
echo ""
echo "**異常交易統計**：$(wc -l < anomalies.csv) 筆，"
echo "總金額 $(awk -F',' '{s+=$4} END{printf "$%,d", s}' anomalies.csv)"
模擬輸出 · OUTPUT
日期產品數量金額
2026-08-01Server A3$15,000
2026-08-05License X10$42,000

異常交易統計：2 筆，總金額 $57,000

為什麼選這條路徑：awk 比 grep 更適合處理 CSV——grep 是文字匹配，遇到欄位邊界容易誤判（例如金額 9999 但名稱含 10000）。用 -F',' 指定逗號分隔後，$4 精確取到金額欄，數學比較 > 10000 才準確。最後用 printf 直接輸出 Markdown 表格格式，省去再加工的步驟。

為什麼不用 Python/Excel：如果只是單次快速分析，命令列 3 行搞定、不需要開環境。但若需定期執行或邏輯複雜（如多欄位條件篩選），建議改用 Python + pandas，可讀性與維護性更好。

深入原理擴充

強調語法的巢狀解析規則

Markdown 渲染器處理 ** 和 * 時，內部其實在跑一套Delimiter Run（分隔符運算）演算法。根據 CommonMark 規範：

  1. 掃描全文找所有 * 和 ** 的位置，標記每個分隔符的「左開」或「右關」屬性。
  2. 左開分隔符必須：前方是空白或行首；右關分隔符必須：後方是空白或行尾（或標點）。
  3. 配對時，內層先配——所以 **粗體 *斜體* 粗體** 是合法巢狀。
容易忽略的邊界案例：*a *b* c* 在 CommonMark 規範中，第一個 * 是左開，第二個是右關（配對出「a b」），第三個無法配對所以原樣輸出。結果是「a b c*」而非預期的「a b c」。這就是為什麼建議：巢狀強調時，內層符號要完全包在外層內部，不要交叉。

診斷式疑難排解表

症狀可能原因解決方案
按 Enter 兩行卻合併成一段Markdown 只認空行為段落分隔，單次換行會合併在兩段之間插入一個空行

進階挑戰題

挑戰 1：寫一份「烹飪步驟」文件，混合使用有序清單（步驟順序）、無序清單（食材清單）、巢狀清單（子步驟）、粗體（關鍵提醒）和分隔線。要求：至少 3 層巢狀、至少 2 次強調。
挑戰 2：用 Markdown 寫一份「比較三種程式語言」的文件，每種語言用一個 H2 標題，下方放一個特性對比表格（至少 5 列 4 欄），表格後接一段引用區塊寫你的推薦理由。練習標題、表格、引用三種語法的組合。
挑戰 3：故意寫一份「有 5 處常見錯誤」的 Markdown 文件（缺空行、底線強調、分隔線缺空行等），然後寫出對應的修正版，並在每個修正旁用引用區塊說明為什麼原本是錯的。

① 專案級端到端 Worked Example

專案：個人知識庫（Obsidian Vault）— 從零建立一套可版本控制的筆記系統

這個專案把本單元的「標題層級、強調、段落、有序/無序/巢狀清單、分隔線」全部用在真實場景：一套每天使用的筆記系統。結構越正確，未來的自己越容易找、機器越好搜。

產出檔案樹 · FILE TREE
vault/
├── README.md            ← 知識庫導覽（H1 唯一）
├── 001-入門.md          ← 本篇重點
├── 002-進階.md
├── 003-專案筆記.md
└── templates/
    └── 每日筆記.md     ← 範本：標題 + 清單結構
001-入門.md · KEY FILE
# 知識庫入門

**目標：** 用 Markdown 管理所有長期筆記。

## 為什麼選純文字
- 永不壞檔
- 版本控制友善
- 任何裝置可開

## 今日任務
1. 建立第一個筆記
   1. 取檔名
   2. 寫唯一的 H1
2. 建立每日範本

---

明天繼續：**雙向連結**。
驗證命令 · VERIFY
$ markdownlint "vault/**/*.md"
✅ 6 個檔案、0 error

# 每個檔案只能有一個 H1
$ awk '/^# /{c++} END{print "H1 數量:", c}' 001-入門.md
H1 數量: 1

# 追蹤筆記的演進
$ git log --oneline --follow 001-入門.md
f1a2b3c 加入雙向連結章節
d4e5f6a 初版知識庫
拆解 · ANATOMY

① 唯一 H1 = 文件主題
② 粗體標出「目標」與「雙向連結」
③ 無序清單 → 特點；有序清單 → 步驟
④ 巢狀有序清單 = 子步驟
⑤ --- 分隔「今天」與「明天」

為什麼這是「專案級」：知識庫不是一份文件，而是一套「以正確結構運作」的系統——唯一的 H1 讓搜尋與連結有穩定錨點，統一的清單縮排讓渲染永不跑版，而版本控制讓筆記可以回溯。這些都是本單元語法在「系統規模」下的組合運用。

延伸：Obsidian 的 [[雙向連結]] 是方言擴充（單元 6/7 會談到），但底層的標題與清單永遠是標準 CommonMark——先學好基礎，擴充只是加分。

② 效能/品質/安全深度

本單元主題：效能 — 大型文件的解析與渲染效能

Markdown 解析大致是線性的，但某些結構會讓成本暴漲：

  • 巢狀深度：每多一層巢狀清單，AST 與 DOM 深度 +1。超過 6-8 層時，遞迴解析與瀏覽器排版都會明顯變慢——把巢狀壓在 3 層內。
  • 單檔大小：一個 10 萬行的 .md 檔，行內解析（強調、連結的貪婪匹配）會吃掉大量 CPU。實務上單檔以 300-500 行為佳，長內容拆成多檔。
  • 行內 token 數量：一段文字內塞太多 **、[links]、`code`，token 數目爆量，可讀性也差——濃縮表達。
  • 實測參考：markdown-it 對一般文件約每秒數 MB，但如果文件含「長段落 + 大量行內標記」，可能退化為接近二次方。
效能與結構是同一件事：效能建議（少巢狀、短段落、拆檔）恰好也是文件品質建議。如果你發現某個 .md 渲染很慢，先檢查結構——不是換渲染器。
