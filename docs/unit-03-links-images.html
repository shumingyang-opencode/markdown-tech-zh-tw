3.1 行內連結 · Inline Links

行內連結把網址直接嵌在文字裡，是最常用的形式：[顯示文字](網址)。

原始碼 · SOURCE
前往 [GitHub](https://github.com)
這是 [Markdown 官方](https://daringfireball.net/projects/markdown/)
渲染結果 · RENDERED

前往 GitHub
這是 Markdown 官方

行內連結可加標題（title）——滑鼠懸停時顯示提示：[文字](網址 "提示")。

3.2 參照式連結 · Reference Links

參照式連結把網址「定義」在文末，正文只寫 [文字][id]。長文件、同一網址出現多次時最實用——改一次定義全部更新：

原始碼 · SOURCE
我用 [GitHub][1] 與 [GitLab][2]。
[GitHub][1] 是微軟的，[GitLab][2] 是開源的。

[1]: https://github.com
[2]: https://gitlab.com "GitLab 官網"
渲染結果 · RENDERED

我用 GitHub 與 GitLab。
GitHub 是微軟的，GitLab 是開源的。

何時用參照式：同一網址出現多次、或文件很長時。短文件用行內即可。定義放文末，可加 title。

3.3 圖片 · Images

圖片語法 = 連結前面加 !，中括號內是 alt 文字（無法載入時顯示、利於無障礙）：

原始碼 · SOURCE
![OpenCode 標誌](/assets/favicon.svg)
![備用文字](missing.png "標題提示")
渲染結果 · RENDERED


（第二張載入失敗會顯示 alt 文字「備用文字」）

GFM 尺寸語法：GitHub 支援 <img width="300"> 直接改尺寸；有些渲染器支援 ![alt](url =100x100)。

3.4 巢狀連結：圖片當按鈕

把「圖片」包在「連結」裡，就能做出點圖片跳轉的效果（README 徽章就是這樣）：

原始碼 · SOURCE
[![點我](assets/favicon.svg)](https://example.com)
渲染結果 · RENDERED

（點圖片 → 跳到 example.com）

3.5 相對路徑 vs 絕對路徑

類型範例適用
相對路徑docs/guide.md、../img/a.png文件與圖片在同 repo/站內——可攜、可隨 repo 移動
絕對路徑（站內）/img/a.png站點根固定時
絕對路徑（外部）https://example.com/a.png外部資源
GitHub 注意：README 內的相對路徑以 repo 根目錄為基準，不是 README 所在資料夾。檔案在 docs/ 就寫 docs/img/x.png。

進階真實情境 Worked Example

情境：批次檢查 repo 中所有 Markdown 檔的連結是否存活

假設你的 docs/ 資料夾有 20 個 .md 檔，裡面共 150 條連結。要快速找出哪些壞掉：

終端 · TERMINAL
# 1. 提取所有 .md 檔中的 URL（行內連結 + 圖片）
grep -rhoP '(?<=\()(https?://[^)]+)' docs/*.md | sort -u > urls.txt

# 2. 同時提取相對路徑的連結
grep -rhoP '(?<=\()((?!\.\.?\./)(?!https?://)[^)]+\.(png|jpg|svg|md))' \
  docs/*.md | sort -u > local.txt

# 3. 用 curl 批次檢查外部連結（平行 + 超時 5 秒）
xargs -n1 -P8 curl -o /dev/null -sL -w "%{http_code} %{url}\n" \
  < urls.txt 2>/dev/null | grep -v "200\|301\|302" > broken.txt

# 4. 顯示壞掉的連結
echo "=== 外部壞連結 ==="
cat broken.txt
echo ""
echo "=== 本地相對路徑（需手動確認）==="
cat local.txt
模擬輸出 · OUTPUT
=== 外部壞連結 ===
404 https://example.com/old-docs
410 https://legacy.api.io/v1

=== 本地相對路徑（需手動確認）===
demo.png
api.md
architecture.svg

為什麼選這條路徑：grep -P（Perl 正則）的前瞻斷言 (?<=\() 只匹配括號內的 URL，不會誤抓到文字中的網址。xargs -P8 開 8 個平行 curl，比逐條測快 5-8 倍。用 sort -u 先去重，避免同一個壞連結重複報告。

替代方案：如果 repo 在 GitHub 上，可以用 markdown-link-check GitHub Action，設定 .mlc.yml 就能在 CI 自動檢查，支援重試、排除清單、本地路徑驗證。

深入原理擴充

Markdown 連結與圖片的內部解析流程

渲染器處理 [text](url) 時的內部流程：

  1. 行內分詞：掃描到 [ 時進入「連結文字模式」，收集到 ] 為止；接著檢查下一個字元是否為 (，是則進入「行內連結 URL 模式」。
  2. URL 提取：收集 ( 內的內容直到匹配的 )。支援 title（用引號包住的額外文字）。
  3. 圖片判斷：如果 [ 前有一個 !，生成 <img> 而非 <a>。
  4. 參照式連結：遇到 [text][ref] 時，去文件末尾找 [ref]: URL 的定義。
容易忽略的邊界案例：圖片 alt 文字內若有 ] 會提前結束匹配。例如 ![img[a]b](url.png) 會被解析為 alt = img[a，然後 b](url.png) 成為普通文字。解法：alt 文字內不要放 ] 字元，或用 HTML <img> 標籤替代。

診斷式疑難排解表

症狀可能原因解決方案
圖片顯示 alt 文字而非圖片相對路徑不對（以 repo 根為基準，非 .md 檔所在位置）確認路徑從 repo 根開始算，或用絕對 URL
連結文字原樣顯示 [文字](網址)中括號和括號之間有換行或多余空格確保 ][ 與 ]( 之間沒有空格或換行
參照式連結未渲染定義 ID 拼錯或找不到對應定義確認 [ref] 和 [ref]: 的 ID 完全一致（含大小寫）
巢狀圖片連結點了沒反應[![alt](img)](url) 中 img 路徑錯，導致圖片壞掉先確認圖片能顯示，再包上連結
GitHub README 內圖片載入很慢圖片檔太大（原始截圖未壓縮）用 squoosh.app 或 sharp 壓縮到 1280px 以內

進階挑戰題

挑戰 1：建立一個「圖片展示頁」，用 Markdown 寫出至少 6 張圖片的畫廊，每張圖片有不同的對齊方式（左、中、右），全部點擊後連結到對應的高清原圖。使用巢狀連結 + 圖片語法。
挑戰 2：為你自己的 repo 寫一份 README，裡面包含：至少 3 個參照式連結（定義放在文末）、2 個巢狀圖片連結（徽章）、1 個相對路徑連結到本地文件、1 個外部絕對連結。然後在另一個 .md 檔中參照同一個 ID，驗證參照式連結的「改一處、全部更新」特性。
挑戰 3：寫一個 shell script，自動掃描指定 .md 檔中的所有相對路徑圖片連結，檢查檔案是否存在，不存在的輸出警告。提示：grep 提取路徑 → test -f 檢查。

① 專案級端到端 Worked Example

專案：個人技術部落格 — 圖片資產管理 + 連結健康自動化

部落格是「連結 + 圖片 + 相對路徑」的大宗使用場景。這個專案把本單元語法提升為一套系統：統一圖片資產、參照式連結管理、CI 自動檢查連結與圖片是否存活。

產出檔案樹 · FILE TREE
blog/
├── README.md
├── content/posts/
│   └── 2026-08-17-first-post.md
├── public/images/
│   ├── hero.png        ← 統一圖片資產
│   └── diagrams/
├── scripts/
│   ├── check-links.sh  ← 檢查內部資源
│   └── optimize-images.sh
└── .github/workflows/

文章 · POST (節錄)
---
title: 我的第一篇文章
date: 2026-08-17
---

![封面](images/hero.png)

詳見[官方文件](https://example.com/docs)，
或先讀[入門指南][guide]。

[guide]: https://example.com/guide
check-links.sh · KEY FILE
#!/bin/bash
# 檢查所有本地圖片與 .md 內部連結是否存在
grep -rhoP '(?<=\()([^)]+\.(png|jpg|svg|md))' content/ \
  | sort -u | while read -r p; do
  [ -f "content/$p" ] || [ -f "public/$p" ] || echo "❌ 缺少: $p"
done
echo "✅ 內部資源檢查完成"
驗證命令與輸出 · VERIFY
$ ./scripts/check-links.sh
✅ 內部資源檢查完成

$ npx markdown-link-check content/**/*.md
[✓] https://example.com/docs       200
[✓] https://example.com/guide      200
✅ 外部連結 2/2 存活

為什麼這是「專案級」：單一文章的連結不會壞，但 50 篇文章、400 張圖的部落格一定會壞。這套系統用「參照式連結集中定義 + 相對路徑統一基準 + CI 自動檢查」三個機制，讓連結健康成為可自動驗證的常態，而不是靠作者事後人工巡。

與第 1 輪範例的層級差異：第 1 輪是「掃一次看看壞了哪些」；這裡是把「掃描 → 檢查 → 擋在合併前」變成每次 PR 都會執行的系統化流程。

② 效能/品質/安全深度

本單元主題：安全 — 連結與圖片的注入與釣魚防護

連結與圖片是 Markdown 中「最容易被惡意利用」的語法，因為它們把「外部內容」拉進你的頁面：

  • 釣魚連結：顯示文字與實際 URL 不符（[google.com](https://evil.example)）。撰寫時誠實，閱讀時確認。
  • 偽協定：[x](javascript:alert(1))。多數現代渲染器已擋掉 javascript:，但自製渲染器需自行過濾。
  • 圖片載入器注入：![x](img "onerror=...") 或直接寫 <img onerror>。GitHub 會消毒，但自建站不會。
  • 追蹤與隱私：第三方圖床（如 tracking pixel）會記錄閱讀行為。敏感文件避免外部資源。
實務準則：對「不可信來源」的 Markdown（使用者投稿、Issue 內容）一律先過 sanitizer（如 DOMPurify），並對 URL 做協議白名單（http/https only）。對「可信作者」的文件則以「誠實撰寫 + 審查」為主。
